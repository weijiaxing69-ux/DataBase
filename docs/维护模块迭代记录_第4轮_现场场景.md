# 维护模块迭代记录（第 4 轮：从真实充电场景出发）

时间：2026-11-16　范围：充电现场问题识别与自动处置

---

## 一、先想清楚：车主真正会遇到什么

按"车主插枪到拔枪"的顺序走一遍，能落在这条业务线上的问题有六类：

| 场景 | 现象 | 现有系统能不能发现 |
|---|---|---|
| 插枪后没充上 | 订单显示充电中，电量不动 | ❌ 设备自报正常，没有故障码 |
| 充电中突然断 | 功率掉到 0，枪还锁着 | ❌ 同上 |
| 绝缘/急停 | 桩直接停，屏幕上红字 | ✅ 有告警，但没人立刻停机、也没派单 |
| 反复修不好 | 同一根桩一个月坏三次 | ❌ 工单一张张修，没人看"复发" |
| 充满不挪车 | 桩被占，后面排队 | 属计费与用户运营，不在本模块 |
| 充得慢 | 功率只有额定一半 | 与温度降额有关，可后续做 |

前四类是本模块该管的，第三、四类尤其要紧：**安全类故障不能等运维到场才停用；反复故障必须升级处理**。

## 二、这轮做的三件事

### 1. 充电中断识别（订单在充、功率为 0）

**为什么需要**：跳枪、枪锁松脱、BMS 通信中断时，设备往往不报故障码，平台看到的是"订单正常进行"，车主看到的却是电量不动。这类投诉在运维工单里占比很高，而且没法靠设备上报发现。

**做法**：后台任务 `check_charging_anomaly`

```sql
-- 订单在充电中，但最近 6 分钟采样功率峰值仍低于 1kW，且至少 2 条采样
select o.order_id, o.gun_id, g.pile_id, count(*) samples, max(r.power_kw) max_power
  from charging_order o
  join charging_gun g on g.gun_id = o.gun_id
  join device_reading r on r.pile_id = g.pile_id and r.sampled_at >= :since
 where o.status = 'charging'
 group by o.order_id, o.gun_id, g.pile_id
having count(*) >= 2 and max(r.power_kw) < :threshold
```

命中即生成 `CHG01` 告警（high，响应 30 分钟）。用 `insert ignore` + 未恢复告警唯一键做幂等，任务每分钟跑也不会刷屏。

**阈值有依据**：交流慢充最低 1.4kW、直流快充起步 20kW，取 1kW 作为"确实没在充"的下限；6 分钟窗口避开启动握手阶段的正常低功率。

### 2. 安全告警自动停机 + 自动派单

**为什么需要**：绝缘故障、急停按下属于"人不能靠近"的级别。现在的流程是告警 → 等运维看到 → 现场处置，中间桩还挂着"可用"，下一位车主可能直接插枪。

**做法**：后台任务 `auto_dispatch_safety_alerts`，对 `severity='critical'` 且尚无工单的告警：

1. 桩置 `fault`、`has_fault=1`，写状态日志（枪级告警同时把枪置 fault）
2. 按值班表找当前主值班与主管（没有当前班次就取最近一次排班，再兜底平台管理员）
3. 直接建工单，接单截止 = 当前时间 + 该告警的响应时限快照

**效果**：从"告警等人处理"变成"先停用再派人"，符合现场安全规程。

### 3. 复发故障升级

**为什么需要**：同一根桩同一故障码一个月出现三次，说明换件或换桩才能解决，但工单系统里只是三张独立工单，没人合并看。

**做法**：后台任务 `escalate_recurring_faults`

```sql
select pile_id, alert_code, count(*) times
  from device_alert
 where occurred_at >= :since
 group by pile_id, alert_code
having count(*) >= 3
```

对命中的桩，把该告警下**未闭环**的工单升级一级（最高 L3），写一条 `escalated` 事件，备注"复发第 N 次（30 天内同码告警）"。用备注前缀做幂等，重复执行不会反复升级。

## 三、验证

| 用例 | 断言 |
|---|---|
| 充电中断 | 订单在充 + 两条 0.2kW 采样 → 生成 CHG01；再跑一次返回 0 |
| 安全停机 | critical 告警 → 桩 fault/has_fault=1、工单 assigned、告警 processing；再跑不重复派单 |
| 复发升级 | 同桩同码 3 次 + 未闭环工单 → 等级 +1、事件含"复发第3次"；再跑返回 0 |

维护模块测试 23 → **26 个**，全量 **92 passed**。

## 四、还没做的（想清楚了再决定）

| 场景 | 为什么先不做 |
|---|---|
| 充满占位提醒 | 涉及占位费与用户通知，属于计费与会员模块，跨模块改动大 |
| 功率不足（降额）识别 | 需要额定功率与温度曲线做基线，样本不足时误报率高 |
| 备件缺货导致停机跟踪 | 需要给工单加"待料"状态，会动状态机契约 |
| 故障预测 | 需要历史故障序列训练，课程设计范围内不现实 |

这四项我都留了口子：占位可以从 `charging_order` + `charging_gun` 读，降额可以用 `device_reading.power_kw` 与 `charging_pile.rated_power_kw` 比，等主模块稳定后再碰。

## 五、这一轮的判断

真实场景里，"设备报障"只是问题的一部分，**更大一块是"设备不报障但确实不能用"**。
这轮三个能力的共同点，都是用**采样数据与历史记录反推**设备没自报的问题——这也是数据库课程里"用数据发现问题"的落地。
