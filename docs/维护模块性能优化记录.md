原则：先测后改。下面的数字都是本机实测，不是估算。

## 一、列表接口的 N+1 问题（工单列表）

### 问题

`list_work_orders` 每行都要查两次事件表（首次接单、首次闭环），一页 20 条就是 40 次查询。

实测（`SHOW SESSION STATUS LIKE 'Questions'` 差值）：

| 场景 | 优化前 | 优化后 |
|---|---:|---:|
| 工单列表，一页 20 条 | **43 次 SQL** | **4 次** |

### 改法

`dao.event_summaries()` 用一次条件聚合取回整页：

```sql
select work_order_id,
       min(case when event_type = 'accepted' then event_at end) as accepted_at,
       min(case when event_type = 'closed'   then event_at end) as closed_at
  from work_order_event
 where work_order_id in (:ids)
 group by work_order_id
```

Service 侧 `_work_order_details(db, rows)` 先批量取摘要，再逐行组装 DTO，单条详情接口仍走原来的 `first_event_at`。

## 二、数据范围过滤：从「先查 ID 列表」改为相关 EXISTS

### 问题

原实现先查出账号可见的全部 `pile_id`，再拼成 `IN (1,2,3,...)`。桩数量一多，SQL 文本变长、无法走索引，而且和分页组合时容易失真。

### 改法

改成相关子查询，由优化器按行判断：

```sql
exists (
  select 1 from charging_pile p
    join station st on st.station_id = p.station_id
   where p.pile_id = device_alert.pile_id
     and (st.station_id  in (select station_id  from sys_account_station  where account_id = :aid)
       or st.operator_id in (select operator_id from sys_account_operator where account_id = :aid))
)
```

工单列表的同款子查询多绕一层 `device_alert`。平台管理员不受限，直接不加该条件。

**验证**：管理员看到 30 条告警，运维账号（只有部分场站授权）看到 24 条，说明范围生效且计数准确。

## 三、排序索引：filesort → 反向索引扫描

### 问题

告警列表按 `occurred_at desc` 分页、工单列表按 `assigned_at desc` 分页，两张表原来都没有对应索引，执行计划是 `type=ALL` + `Using filesort`。

### 基准测试

小表（30 行）看不出差别，所以单独造了一张 **20 万行** 的基准表测：

| 条件 | 执行计划 | 最小耗时 | 平均耗时 |
|---|---|---:|---:|
| 无索引 | `ALL` + `Using filesort` | 55.3 ms | 63.1 ms |
| 有索引 | `Backward index scan; Using index` | **0.2 ms** | **0.4 ms** |

提升约 **150–250 倍**，且数据量越大差距越明显。

### 落地

`database/migrations/16_indexes.sql`（幂等，先判断索引是否存在）：

- `device_alert (occurred_at)`
- `work_order (assigned_at)`
- `inspection_record (inspected_at)`

> 注意：在 30 行的小表上 MySQL 仍可能选择全表扫描，这是优化器的正确决定，不代表索引无效。
> 报告里要写"数据量放大后的对比"，不要只贴小表结果。

## 五、还有哪些可优化（本次未做，留作后续）
