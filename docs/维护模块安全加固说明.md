# 维护模块安全加固说明

对应任务书 3.4「系统登录安全策略与权限控制、敏感字段脱敏」中属于设备运维业务线的部分。
时间：2026-11-16　验证环境：MySQL 8.0.29 + 本机测试库

---

## 一、威胁模型

设备运维模块的入口有三类，风险各不相同：

| 入口 | 谁在用 | 主要威胁 |
|---|---|---|
| 心跳 / 采样上报 | 充电桩设备 | 伪造设备、替别的桩上报、重复上报刷数据 |
| 告警 / 工单查询与处置 | 运维、客服、管理员 | 越权查看他人场站、越权处理别人的工单 |
| 规则配置、后台任务、事件声明 | 管理员 | 非管理员改规则、手动触发任务制造脏数据 |

---

## 二、措施与实现位置

### 1. 设备身份：凭据换主体，不再用人工账号代替

**问题**：原实现的心跳与采样接口用账号令牌放行，任何有权限的账号都能替任意桩上报，等于把设备入口开放给人。

**做法**（`app/modules/maintenance/device.py`）：

- 客户端持有签发时返回的明文令牌，通过请求头 `X-Device-Token` 提交；
- 服务端只存 SHA-256 摘要，比对摘要而非明文（令牌原文不落库、不写日志）；
- 校验 `expires_at` 与 `revoked_at`；
- 返回的 `DeviceActor` 绑定 `pile_id`，服务层再校验请求里的桩号必须一致。

**效果**：拿到 A 桩凭据无法给 B 桩上报（403）；无凭据 401；过期或撤销 401。

### 2. 权限：细粒度权限码 + 角色授权

种子原来只有 4 个 `maintenance.*` 权限码，规则、巡检、报障只能借用 `assign` / `handle`。
`database/migrations/17_security_hardening.sql` 补齐 6 个：

| 权限码 | platform_admin | maintenance_engineer | customer_service |
|---|:--:|:--:|:--:|
| maintenance.rule.manage | ✅ | | |
| maintenance.inspection.read | ✅ | ✅ | |
| maintenance.inspection.create | ✅ | ✅ | |
| maintenance.fault_report.read | ✅ | ✅ | ✅ |
| maintenance.fault_report.handle | ✅ | | ✅ |
| maintenance.incident.manage | ✅ | | |

代码里保留旧码兜底（`_require(新码, 旧码)`），未执行迁移的库也能跑，不会因为权限表没更新直接 500。

### 3. 数据范围：所有列表都按账号授权场站过滤

告警、工单、巡检、报障四个列表统一用相关 `EXISTS` 过滤，覆盖两种授权方式：

- 直接授权场站：`sys_account_station`
- 授权运营商（其下所有场站）：`sys_account_operator`

平台管理员不加限制。**验证**：管理员看到 30 条告警，运维账号只看到 24 条；无任何授权的账号巡检列表 total = 0。

详情与处置入口另有校验：`security.assert_resource_scope` 按桩/枪反查场站，越权直接 403，不依赖前端隐藏按钮。

### 4. 完整性：重复上报幂等，不返回 500

采样表加唯一键 `uq_device_reading_pile_sampled (pile_id, sampled_at)`。
同一桩同一毫秒重复上报时，服务捕获唯一键冲突并返回 `{"accepted": false, "duplicate": true}`，而不是抛 500。
唯一键包含全部分区列（`sampled_at` 为 RANGE、`pile_id` 为 HASH），满足分区表约束。

### 5. 最小暴露与审计

- 错误只返回中文提示与状态码，不带 SQL、堆栈、令牌；
- 工单事件与应急动作都记录 `actor_account_id`，系统任务写 NULL，可追溯"谁在什么时候做了什么"；
- 高风险动作（隔离场站、关闭事件）在应急模块要求填写审批人，且申请人不得自批（CHECK 约束）。

## 三、端到端验证

用真实 HTTP 跑了一遍（`platform_admin_demo` 登录后签发凭据）：

| # | 场景 | 预期 | 实际 |
|---|---|---|---|
| 1 | 管理员签发桩 15 的设备凭据 | 返回明文令牌一次 | 成功，令牌只出现一次 |
| 2 | 不带 `X-Device-Token` 上报心跳 | 401 | **401** |
| 3 | 带凭据上报自己的桩 | 200 且返回 sample_id | **200 / sample_id=269** |
| 4 | 同一采样时刻重复上报 | duplicate=true，库里 1 条 | **duplicate=true** |
| 5 | 用桩 15 的凭据上报桩 16 | 403 | **403** |
| 6 | 运维账号手动触发后台任务 | 403 | **403** |

自动化测试同步覆盖（`backend/tests/maintenance`）：12 个用例，含无效/过期/撤销凭据、越权桩、重复上报、范围过滤、管理员专属任务。

## 四、这次修复的一个隐藏 bug（值得写进报告）

`_tx` 原实现用 `db.in_transaction()` 判断是否该提交。但 SQLAlchemy 的 autobegin 会在**任何 SELECT 之后**把会话标记为"已在事务中"，于是：只要服务函数开头查过一次（几乎每个写操作都会），`_tx` 就认为"外层已开事务"，直接 yield 而不提交，写入最终随请求结束被回滚。

这个 bug 在只读接口和同会话测试里完全看不出来，是"重复上报"用例（需要跨连接确认数据是否落库）把它暴露的。修法是改用显式的嵌套计数，而不是依赖 `in_transaction()`。

## 五、本次没做（超出课程设计范围）

- HTTPS / TLS 终止：由部署层负责，本地演示用 HTTP；
- 接口限流与防重放：需要网关或中间件，非数据库课程重点；
- 设备凭据轮换与吊销接口：表已支持 `revoked_at`，但未做管理页面；
- 敏感字段加密：手机号、车牌属于用户模块（成员4），本模块不落这些字段；
- 审计日志留存周期与归档：属于运维策略，报告中说明方案即可。
