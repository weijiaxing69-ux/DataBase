# 成员4：用户会员模块实现规划

> 适用版本：V1.4 统一数据字典与接口函数规范
> 负责人：成员4（用户会员）
> 目标：完成 membership 模块的数据库、后端、前端、数据库对象、测试及个人报告材料。

> 当前进度（2026-11-19）：V1.4 会员基线模块已完成；现补充余额退款申请和服务申诉跟踪两个会员自助功能。扩展数据库迁移及验收结果见 `成员4_阶段实现与验收记录.md`。

- 本模块 DAO、Service、HTTP API、Vue 页面、视图、存储过程、触发器、单元测试和联调测试。
- 个人课程设计报告中与本人工作相关的数据库设计、实现和测试内容。

### 1.2 需要协作但不改动对方模块

| 合作方 | 交互内容 | 模块边界 |
| --- | --- | --- |
| 成员1 | 项目骨架、统一建库/装载脚本、公共客户端、路由合并、集成；安全公共接口和 Actor/DTO 契约 | 不自行改公共接口；membership DDL 的装载顺序由统一入口管理 |

## 2. 数据库对象范围

### 2.1 负责的 24 张表

| 业务域 | 表 |
| --- | --- |
| 账号、RBAC、登录会话（9） | `sys_account`、`sys_role`、`sys_permission`、`sys_account_role`、`sys_role_permission`、`sys_account_operator`、`sys_account_station`、`sys_account_fleet`、`sys_session` |
| 车主和车辆（3） | `app_user`、`vehicle`、`vehicle_binding` |
| 活动和优惠券（4） | `promotion`、`promotion_station`、`user_coupon`、`coupon_usage` |
| 车队与额度（6） | `fleet`、`fleet_card`、`fleet_authorization`、`fleet_quota_month`、`fleet_quota_reservation`、`fleet_quota_adjustment` |
| 钱包与评价（2） | `wallet_transaction`、`service_feedback` |

### 2.2 建表与数据约定

- 字段、类型、默认值、主外键、唯一约束、CHECK、索引按 V1.4 数据字典实现；外键默认 `RESTRICT`，历史和财务记录不做级联物理删除。
- 数据库存 UTC，使用 `datetime(3)`；连接时区设为 UTC。账期按 `Asia/Shanghai` 计算，`bill_month` 使用当月首日。
- 金额使用 `Decimal` 与 `decimal(14,2)`；金额、余额、状态和审计字段由服务端控制，不能接受客户端任意覆盖。
- 手机号、车牌和企业联系人电话加密保存，使用带密钥摘要做精确检索；接口只返回脱敏值。测试数据使用合成数据和专用测试密钥。
- 会员余额是缓存，必须与 `wallet_transaction` 保持一致。钱包流水和历史发放/核销记录按业务留痕，不物理删除。
- 测试数据中 membership 共 500 行；固定角色 `sys_role` 只有规范规定的 6 行，是有意例外，不能为满足“每表 20 行”要求添加虚假角色。
- membership 中有指向 `charging_order`、`payment_record`、`refund_record`、`station` 等其他模块的外键。先由组长将所有表创建完，再统一添加外键和导入种子数据。

### 2.3 建议的数据视图

1. `v_membership_user_overview`：供授权管理角色查看用户状态、会员等级、实名状态、注册时间和车辆数量；不输出手机号、车牌明文。
2. `v_membership_coupon_summary`：按活动汇总发放、可用、锁定、核销、过期数量和核销率；不暴露持券人敏感信息。
3. `v_membership_fleet_quota_summary`：按车队、授权和账期汇总额度、预占、已用及剩余额度；访问仍须由后端执行范围检查。

视图采用明确列清单，避免 `SELECT *`；验证多表汇总时不重复计数。最终名称和字段在与组长确认后固定。

### 2.4 建议的存储过程与触发器

- 存储过程：`sp_issue_promotion_coupons`。锁定活动记录，检查活动已审核且有效、总发放量和每人上限；在同一事务内增加 `issued_count` 并写入 `user_coupon`，保存发放时面额和门槛快照。过程不自行提交事务，由调用方控制事务边界。
- 触发器：为 `wallet_transaction` 建立防篡改触发器，禁止事后修改流水金额/业务来源；删除也应拒绝或按统一归档规则处理。若采用更新和删除两个触发器，在报告中说明它们共同保护余额流水完整性。
- Service 与存储过程不能各自维护两套互相冲突的发券规则；确定由 Service 调用过程，或由 Service 实现并把过程留作独立演示，不能让两个入口都被生产流程调用。

## 3. 后端功能实现

### 3.1 登录与 RBAC

- 登录校验账号状态、密码哈希、失败次数和锁定时间；成功后更新最后登录时间并创建会话。
- 会话表只存 JWT `jti` 摘要，不存明文 Token；登出时撤销当前会话，账号禁用后拒绝后续请求。
- 固定角色代码：`platform_admin`、`maintenance_engineer`、`customer_service`、`vehicle_owner`、`fleet_admin`、`operator_manager`。权限代码按 `模块.资源.动作` 命名。
- 登录后构造 Actor/AccountContext，后端逐请求检查权限代码和资源归属；`sys_account_operator`、`sys_account_station`、`sys_account_fleet` 提供数据范围。
- 匿名注册只创建车主账号并授予 `vehicle_owner`；实名验证是授权客服执行的模拟流程。
- 密码使用 Argon2id 或 bcrypt 哈希；对失败登录执行计数、阈值锁定和到期解锁策略。登录状态、禁用状态和 Session 撤销必须一致。

### 3.2 车主、资料和车辆

- 注册时完成账号和车主档案的原子创建，规范化手机号后校验唯一性并加密保存。
- 个人资料更新采用字段白名单；本人不能写入 `balance`、`real_name_status`、账号状态或权限字段。
- 车辆绑定写入 `vehicle_binding` 历史；同一车辆同时只能存在一条有效归属。并发抢绑由唯一生成列/约束兜底，并在 Service 转成统一业务错误。
- 解绑要求本人有权操作且不存在冲突中的充电订单；解绑只结束有效绑定，不删除历史。
- 车主读取车辆时只返回本人车辆或本队授权车辆；禁止仅依据前端传入的 user_id 决定归属。

### 3.3 活动与优惠券

- 活动支持草稿、送审、启用、拒绝、停用状态；审核人和创建人分离，适用场站通过 `promotion_station` 管理。
- 领取/发放校验活动有效期、场站适用范围、总量和每人上限；高并发领取时锁活动行，不能超发。
- 优惠券保留发放时的面额、门槛快照；活动后续编辑不能改变已发券条件。
- 个人优惠券核价时进入 `locked`，订单付清后才核销；部分支付维持锁定；取消或允许释放的超时场景释放；重复回调不重复核销。
- 车队订单禁止使用个人优惠券。全额退款时仅当原券仍在有效期内才补发，且最多补发一次；保留原券和核销历史。

### 3.4 车队授权与月额度

- 车队管理员只能管理授权范围内的车队；车队卡、用车人、车辆授权和有效期需一起校验。
- 启动订单前验证车队卡、授权用户、授权车辆、有效期与状态；按服务端配置预占金额并锁定相应月份额度。
- 正常启动不得使“已用＋预占”超过额度；余额不足拒绝启动。实际充电事实导致超额时保留订单和采样，标记待人工复核，不丢弃真实业务记录。
- 订单结束后把预占结转为实际使用；跨月时从预占月迁移到结束月份，并向 `fleet_quota_adjustment` 写留痕。
- 退款额度调整以 `refund_id` 唯一记账；重复退款回调不重复冲减已用额度。

### 3.5 钱包和评价

- 只实现开发环境模拟充值，不接真实资金渠道；模拟充值接口仅允许本人操作。
- 钱包支付时锁定用户余额，余额不足返回统一业务错误（规范示例为 HTTP 409）；支付记录、负向流水和余额更新处于同一事务。
- 退款仅按原支付渠道处理；原支付为钱包时记正向余额流水。以支付/退款业务键保证幂等。
- 评价只能由订单所属用户创建，每个订单最多一条，评分限制为 1–5 分。

### 3.6 会员自助业务扩展

- **余额退款申请**：车主提交未使用余额退款申请并查询待审核、处理中、已完成或已拒绝状态；待审核和处理中金额都占用可用余额，避免申请期间又被钱包支付花掉。客服审核驳回时释放占用；开发环境模拟通过时，锁定车主余额、更新余额并写负向钱包流水，三者处于同一事务。按用户请求键防止重复提交，按退款申请编号防止重复记账。
- **服务申诉跟踪**：车主提交费用争议、充电服务、账号/优惠券或其他问题，可选关联本人订单；客服记录受理、处理中、解决或驳回状态及回复，时间线保留提交与处理记录。此处只负责会员的申诉受理和查询，不接管设备维修工单。
- 扩展表单独放在 `database/migrations/20261119_member4_self_service.sql`，不修改 V1.4 的 24 张基线表；权限通过 `06_permissions.sql` 幂等补充。

## 4. API 与前端页面

### 4.1 API 按功能组实现

所有路径、方法、Schema 和返回 DTO 以 V1.4 第 5 章为准，不擅自重命名。

- **认证和账号权限**：登录、当前账号、登出；账号列表/详情/创建/状态修改/角色分配/资源范围分配；角色和权限列表/详情。
- **车主与车辆**：注册、个人档案读取/修改、模拟实名、车辆列表/详情、绑定、解绑。
- **活动和优惠券**：活动列表/详情/创建/修改/审核、优惠券列表、领取、定向发放。
- **车队和额度**：车队列表/详情/创建/修改；卡列表/详情/创建/修改；授权列表/详情/创建/修改；设置和查询月额度。
- **钱包和评价**：模拟充值、钱包流水查询、评价列表/详情/创建；另扩展余额退款申请、客服审核及状态查询。
- **服务申诉扩展**：提交费用/服务争议、查看申诉详情和处理时间线、客服受理与回复。

V1.4 基线包含 48 个 membership/auth 接口；本次另增加 7 个退款和申诉接口，共 55 个。基线接口逐项以规范的 `### 5 membership HTTP接口` 为准；扩展接口与 DTO 见会员模块实现和验收记录。

### 4.2 前端路由

实现 V1.4 规范中的 14 个路由，并扩展余额退款申请和服务申诉跟踪两个路由页面：

- `/login`、`/register`
- `/auth/accounts`、`/auth/roles`
- `/membership/profile`、`/membership/vehicles`、`/membership/coupons`、`/membership/promotions`
- `/membership/fleets`、`/membership/fleets/:fleetId`、`/membership/fleet-cards`、`/membership/fleet-authorizations`
- `/membership/wallet`、`/membership/feedbacks`
- `/membership/wallet/refund-requests`、`/membership/appeals`（会员自助扩展）

按钮和路由元信息可以按权限隐藏，但最终授权必须由服务端检查。手机号、车牌只显示脱敏结果；前端不得提交服务端控制字段。

## 5. 查询与数据库设计作业

课程任务书要求至少 5 条连接 3 张及以上关系的复杂 SQL。成员4按组内规范准备 3 条 membership 查询，每题给出两种写法（例如 JOIN 与 CTE/子查询），并提供执行计划和优化说明：

1. 按用户汇总有效车辆、可用优惠券数量和会员状态。
2. 按活动及适用场站统计发放数、核销数和核销率。
3. 按车队与账期统计授权人数、额度、预占、已用和剩余额度。

会员模块自己的逻辑设计材料还要列出关系模式、主键/外键、函数依赖和规范化过程。特别说明余额缓存、额度汇总/预占、优惠快照等字段的业务理由；不能只凭 ER 图或“主键决定其他字段”就宣称全部物理表已满足第三范式。

## 6. 测试计划与验收标准

### 6.1 模块单元/接口测试

- 登录：正确密码、错误密码、连续失败锁定、锁定期内拒绝、禁用账号拒绝、会话到期、登出撤销。
- 权限：车主不能读写他人资料/车辆/优惠券；车队管理员不能跨车队读写；客服实名权限有效；账号没有权限或数据范围时后端拒绝。
- 隐私：密文不以明文落库；摘要唯一检索；API/视图不输出手机号或车牌明文。
- 车辆：一人多车成功、重复/并发抢绑失败、解绑留历史、进行中订单时不能解绑。
- 活动/优惠券：活动未审核不可领；活动总量和每人上限不超发；限定场站校验；快照稳定；部分支付不核销；全额支付只核销一次；释放与退款补券幂等。
- 车队额度：无效/过期授权拒绝；额度不足拒绝；并发预占不超额；跨月迁移有留痕；实际超额转复核；退款只调整一次。
- 钱包/评价：余额不足拒绝；并发扣款不产生负余额；重复支付/退款回调不重复流水；只能模拟充值；跨用户评价拒绝、重复评价拒绝、评分范围检查。

### 6.3 数据导入与整体验收

- 使用 `charging_platform_test` 独立空测试库，由成员1统一装载完整 DDL、外键/索引、视图/过程/触发器及 seed；不要在已有同名表的数据上重复初始化，不使用 `mysql --force`。
- 先运行历史一致性验收查询，再通过应用接口生成 L01/L02 的新记录；单纯运行 seed 或验收 SQL 不等于业务流程已通过。
- 验证会员表数量/行数、外键和约束、余额与流水一致、优惠券和额度不重复记账、关键查询执行计划。

## 8. 关键公共函数契约

以下为 V1.4 已登记的跨模块辅助函数，参数与返回 DTO 以规范为准，不自行改变签名：

- 车队：`validate_fleet_authorization`、`reserve_fleet_quota`、`settle_fleet_quota`、`release_fleet_quota`、`adjust_fleet_quota_after_refund`。
- 优惠券：`lock_coupon_for_order`、`redeem_coupon_for_order`、`release_coupon_for_order`、`reissue_coupon_after_full_refund`。
- 钱包：`debit_wallet_for_payment`、`credit_wallet_for_refund`。

统一按同一事务执行；失败抛统一业务异常并由最外层回滚。请求幂等键、外部支付/退款流水号、订单/退款唯一约束都要参与防重，不能只依赖前端按钮防重复。
