# 成员4：会员模块逻辑设计与规范化说明

## 1. 关系模式和键

下表按 V1.4 的物理表设计整理。`PK` 为主键；`FK` 标出主要参照关系。跨模块关系由组内统一 DDL 在创建完所有实体表后添加。

| 关系 | 主键 | 主要外键 / 约束 |
| --- | --- | --- |
| `sys_account` | `account_id` | `username` 唯一；账号状态受约束 |
| `app_user` | `user_id` | `account_id → sys_account.account_id`（可空且唯一）；`phone_hash` 唯一 |
| `vehicle` | `vehicle_id` | `plate_hash` 唯一；容量、功率为正数 |
| `vehicle_binding` | `binding_id` | `user_id → app_user`；`vehicle_id → vehicle`；有效绑定车辆通过生成列唯一 |
| `promotion` | `promotion_id` | `created_by / reviewed_by → sys_account`；发放数、面额、有效期受约束 |
| `promotion_station` | (`promotion_id`, `station_id`) | `promotion_id → promotion`；`station_id → station`（assets） |
| `user_coupon` | `coupon_id` | `promotion_id → promotion`；`user_id → app_user`；`reissue_source_order_id → charging_order` 且唯一 |
| `coupon_usage` | `usage_id` | `coupon_id → user_coupon`；`order_id → charging_order`；活动状态下的券和订单分别唯一 |
| `fleet` | `fleet_id` | `credit_code` 唯一；联系人电话加密保存 |
| `fleet_card` | `card_id` | `fleet_id → fleet`；`card_no` 唯一；有效期受约束 |
| `fleet_authorization` | `authorization_id` | `card_id → fleet_card`；`user_id → app_user`；`vehicle_id → vehicle` |
| `fleet_quota_month` | `quota_month_id` | `authorization_id → fleet_authorization`；(`authorization_id`, `bill_month`) 唯一 |
| `fleet_quota_reservation` | `reservation_id` | `order_id → charging_order` 且唯一；`quota_month_id → fleet_quota_month` |
| `sys_role` | `role_id` | `role_code` 唯一；仅保留 V1.4 固定的六种角色 |
| `sys_permission` | `permission_id` | `permission_code` 唯一 |
| `sys_account_role` | (`account_id`, `role_id`) | 分别参照 `sys_account`、`sys_role` |
| `sys_role_permission` | (`role_id`, `permission_id`) | 分别参照 `sys_role`、`sys_permission` |
| `sys_account_operator` | (`account_id`, `operator_id`) | 分别参照 `sys_account`、`operator`（assets） |
| `sys_account_station` | (`account_id`, `station_id`) | 分别参照 `sys_account`、`station`（assets） |
| `sys_account_fleet` | (`account_id`, `fleet_id`) | 分别参照 `sys_account`、`fleet` |
| `sys_session` | `session_id` | `account_id → sys_account`；JWT 的 `jti` 摘要唯一 |
| `wallet_transaction` | `wallet_transaction_id` | `user_id → app_user`；`payment_id → payment_record`；`refund_id → refund_record`；`business_key` 唯一 |
| `wallet_balance_refund_request` | `refund_request_id` | `user_id → app_user`；`reviewed_by_account_id → sys_account`；(`user_id`, `request_key`) 唯一 |
| `membership_service_appeal` | `appeal_id` | `user_id → app_user`；可选 `order_id → charging_order`；`assigned_account_id → sys_account`；(`user_id`, `request_key`) 唯一 |
| `membership_service_appeal_event` | `appeal_event_id` | `appeal_id → membership_service_appeal`；`actor_account_id → sys_account`；记录每次状态变化 |
| `fleet_quota_adjustment` | `quota_adjustment_id` | `quota_month_id → fleet_quota_month`；可选参照订单、退款和操作账号；`business_key` 唯一 |
| `service_feedback` | `feedback_id` | `order_id → charging_order` 且唯一；`user_id → app_user`；评分为 1–5 |

完整字段、类型、默认值、CHECK 和索引以 `database/modules/membership/01_tables.sql`、`02_foreign_keys.sql` 与 V1.4 统一数据字典为准。

## 2. 函数依赖示例

下列依赖说明每个实体的非键属性由候选键决定。省略 `created_at`、`updated_at` 等由数据库维护的审计属性时，含义不变。

- `sys_account`：`account_id → username, password_hash, status, failed_attempts, locked_until, last_login_at`；因 `username` 唯一，也有 `username → account_id, ...`。
- `app_user`：`user_id → account_id, display_name, phone_cipher, phone_hash, real_name_status, registration_channel, registered_at, member_level, balance, status`。非空 `account_id`、`phone_hash` 是候选键。
- `vehicle`：`vehicle_id → plate_cipher, plate_hash, model_name, battery_capacity_kwh, max_charging_power_kw, supports_fast_charge, status`；`plate_hash` 也是候选键。
- `promotion`：`promotion_id → promotion_name, face_amount, minimum_spend, valid_from, valid_until, issue_limit, issued_count, per_user_limit, all_stations, redemption_rule, status, created_by, reviewed_by, reviewed_at, review_note`。
- `user_coupon`：`coupon_id → promotion_id, user_id, received_at, expires_at, face_amount_snapshot, minimum_spend_snapshot, status, reissue_source_order_id`；非空 `reissue_source_order_id` 唯一，用于退款补券防重。
- `fleet_quota_month`：`(authorization_id, bill_month) → limit_amount, reserved_amount, used_amount`。它以唯一约束和 surrogate PK `quota_month_id` 表示同一账期只有一份额度记录。
- `fleet_quota_reservation`：`order_id → quota_month_id, reserved_amount, actual_amount, status, reserved_at, settled_at, released_at`，由订单唯一约束保证同一订单至多一条额度占用。
- `wallet_transaction`：`wallet_transaction_id → user_id, payment_id, refund_id, transaction_type, amount, balance_after, business_key, occurred_at`；`business_key` 是幂等候选键，流水不可更新或删除。
- `wallet_balance_refund_request`：`refund_request_id → user_id, amount, reason, status, request_key, reviewed_by_account_id, review_note, created_at, reviewed_at, completed_at`；`(user_id, request_key)` 是会员范围内的幂等候选键。
- `membership_service_appeal`：`appeal_id → user_id, order_id, category, subject, description, status, request_key, assigned_account_id, last_response, created_at, updated_at`；`(user_id, request_key)` 是会员范围内的幂等候选键。
- `membership_service_appeal_event`：`appeal_event_id → appeal_id, actor_account_id, from_status, to_status, message, created_at`；每条记录保留一项处理状态变化。
- `service_feedback`：`order_id → feedback_id, user_id, rating, content, created_at`，由每单唯一约束保证一笔订单最多一条评价。
- RBAC 关联关系如 `sys_account_role`：`(account_id, role_id) → created_at, updated_at`。复合主键防止同一账号重复分配同一角色。

## 3. 规范化说明

1. **第一范式（1NF）**：每个字段存单值；例如 `promotion_station` 和三个账号资源范围表将场站、运营商、车队编号拆成独立关系，不在账号或活动表中存逗号分隔列表。
2. **第二范式（2NF）**：单列主键表的普通字段依赖整键；复合键关联表不包含只依赖复合键一部分的业务属性。例如 `sys_role_permission` 只记录角色与权限的关联，不复制角色名称或权限名称。
3. **第三范式（3NF）**：普通非键属性不经由另一个非键属性传递决定实体属性。用户档案、车辆、车队、角色和权限各自在本实体保存；`fleet_authorization` 只引用用户、车辆和车队卡的键，不复制姓名、车型或企业联系人字段。
4. **历史快照与缓存**：`user_coupon` 的面额/门槛快照是发券时事实，即使活动以后调整也不能反向改变已发券；`app_user.balance`、`promotion.issued_count` 和月额度预占/使用字段是供并发控制和快速判断使用的派生缓存，必须与同事务内的流水/占用记录一起更新。它们属于明确的业务冗余，不能单凭“主键决定非键字段”掩盖一致性义务。
5. **生成列与唯一索引**：`vehicle_binding.active_vehicle_id`、`coupon_usage.active_coupon_id`、`active_order_id` 从本行状态生成，用于表达“当前有效关系唯一”；它们不是客户端可写字段。生成列依赖本行主键确定的业务事实，服务端仍需维护生命周期状态。
6. **会员自助扩展**：退款申请与服务申诉通过独立关系保存，不把客服处理历史塞进会员档案；申诉多次处理记录拆成 `membership_service_appeal_event`，保留可追溯时间线。

## 4. 会员余额退款与服务申诉

- 退款申请状态依次为 `pending_review`（待审核）、`processing`（处理中）、`completed`（已完成）或 `rejected`（已拒绝）。待审核和处理中金额都作为钱包占用额；拒绝时释放，开发环境模拟完成退款时在同一事务内扣减余额并写一条负数 `refund` 钱包流水。
- 每笔退款流水使用 `wallet_balance_refund_request:{refund_request_id}` 唯一业务键；重复审核不会二次扣款。相同会员重复提交 `request_key` 返回原申请，不同金额或原因复用键则拒绝。
- 服务申诉支持费用争议、充电服务、账号/优惠券和其他类别；可选关联订单时先验证订单属于当前会员。每次客服状态变更和回复写入 `membership_service_appeal_event`，详情页按时间展示进度。

## 5. 约束如何落实到业务事务

- 用户/车辆绑定以生成列唯一约束应对并发抢绑；业务层将冲突转成统一 409 错误，解绑保留历史。
- 发券过程锁定活动和用户行，再检查总量与每人上限；券的金额门槛从活动快照读取。
- 锁券、核销、释放和退款补券均由同一 Session 调用；券在订单全额付清后核销，重复支付回调不会重复改变券状态。
- 车队月额度行使用 `FOR UPDATE` 锁；预占按 `order_id` 幂等，结算处理跨月转移并写 `fleet_quota_adjustment`，超额度实际结算保留业务事实并标记人工复核。
- 钱包余额更新和不可变流水插入在调用方同一事务，支付/退款用业务键防重；余额不足按 409 拒绝。
- 钱包支付会扣除所有待审核与处理中退款金额后再判断可用余额，避免会员把已申请退款的金额再次消费。
