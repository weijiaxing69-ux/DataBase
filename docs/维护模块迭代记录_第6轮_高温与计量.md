# 维护模块迭代记录（第 6 轮：高温、计量与占位）

时间：2026-11-16　范围：三个"设备不报障但已经不正常"的场景

---

## 一、场景与判断依据

### 1. 高温预警：等报故障码就晚了

**现象**：夏天午后，模块温度爬到 65℃ 以上，桩开始降额（充得慢），但还没到报故障码的程度。
等报 E0xx 时，往往已经是风扇卡死或功率模块损伤。

**做法**：`check_temperature_warning` 取每根桩最近 3 条采样，全部超过 65℃ 就生成 `TEMP01`（high）。
`row_number() over (partition by pile_id order by sampled_at desc)` 只取最新几条，不扫全表。

**阈值依据**：功率模块常见降额区间是 60–65℃，故障保护多在 75℃ 以上；取 65℃ 是"开始不舒适"的点，留出处置窗口。

### 2. 计量异常：订单结束了，电还在输出

**现象**：车主结束充电、订单变成 `paid`，但采样里仍有 5A 以上电流。可能是继电器粘连，也可能是计量漂移。
前者是**安全隐患**（人拔枪可能拉弧），后者是**计费纠纷**源头。

**做法**：`check_metering_anomaly` 找"该桩没有任何 `charging` 订单，但最近 15 分钟采样电流 > 1A"的桩，
生成 `MET01`（critical）。

**链路**：因为是 critical，`auto_dispatch_safety_alerts` 会在下一轮把桩置 `fault` 并自动派单——检测与处置自动接上。

**阈值依据**：待机电流通常小于 0.5A，1A 以上基本可以排除测量噪声。

### 3. 充满占位：桩被占着，人找不到

**现象**：订单早已结束，桩状态还是 `occupied`。可能是车主没挪车，也可能是枪没归位。
后面的车主看到"占用"直接走人，平台损失一次交易。

**做法**：`check_idle_occupied` 找"桩为 occupied + 无进行中订单 + 上一单结束超过 30 分钟"，
给场站值班发一条站内待办（不生成告警、不生成工单，因为这不是设备故障）。

业务键 `occupy:{桩}:{日期}`，同一天同一桩只提醒一次。

---

## 二、为什么后两个不用告警

告警会触发派单、影响 SLA 统计。占位不是设备故障，用它去占用运维工时不合理，
所以走 `notification`（站内待办）而不是 `device_alert`。这是有意的区分，不是遗漏。

## 三、验证

| 用例 | 断言 |
|---|---|
| 高温预警 | 3 条 71℃ 采样 → 生成 TEMP01（high）；再跑一次为 0 |
| 计量异常 | 无订单 + 6.5A → 生成 MET01（critical）；再跑一次为 0 |
| 充满占位 | 桩置 occupied 且订单已结束 → 生成待办；当天再跑为 0 |

维护模块测试 29 → **32 个**，全量 **98 passed**，前端构建通过。

## 四、任务清单（10 个）

| 任务 | 触发条件 | 产出 |
|---|---|---|
| `offline` | 心跳超时 | 桩离线 + 状态日志 |
| `overdue` | 超时未接单 | 升级 + 事件 + 待办 |
| `recovery` | 观察期满 | 告警恢复 |
| `charging` | 订单在充但功率≈0 | CHG01 告警 |
| `safety` | critical 告警无工单 | 停机 + 派单 |
| `recurring` | 同桩同码 30 天 ≥3 次 | 工单升级 |
| `inspection` | 超 30 天未巡检 | 待办（按月） |
| `temperature` | 连续 3 条 > 65℃ | TEMP01 告警 |
| `metering` | 无订单仍有电流 | MET01 告警（critical） |
| `occupied` | 占位但无订单 | 待办（按天） |

---

## 五、边界说明

- 高温与计量都只读 `device_reading`，不写采样表，避免影响计费口径；
- 计量异常复用安全停机链路，但**不自动关闭订单**——订单归计费模块，跨模块写数据风险太大；
- 占位提醒只发给值班人，不做用户侧通知（那属于会员/消息模块）。
