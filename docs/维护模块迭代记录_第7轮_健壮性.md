## 二、真问题：一条数据失败，整批任务全回滚

### 现象

所有批量任务都是这样写的：

```python
with _tx(db):
    for item in items:
        do_something(item)
```

`_tx` 是最外层事务，**循环里任何一条抛异常，整个事务回滚**，前面处理成功的也一起没了。
更糟的是：如果失败原因是稳定的（比如某条告警引用的桩已被删除、值班表里的账号被停用），
这个任务每分钟都会在同一位置失败，**永久卡死**，后面的数据永远处理不到。

### 修复

引入 `_isolate`：每条用保存点包住，失败只回滚该条并记日志：

```python
def _isolate(db, label, action) -> bool:
    try:
        with db.begin_nested():
            action()
        return True
    except Exception:
        logger.exception("task item failed: %s", label)
        return False
```

已覆盖 4 个最容易出问题的任务：离线判定、超时升级、安全派单、复发升级
（巡检/占位只是发待办，`INSERT IGNORE` 本身不抛异常，暂不包）。

**测试**：造两条 critical 告警，让 `create_work_order` 第一次抛异常，
断言第二条仍然派单成功、返回值为 1。这条用例直接证明了"隔离生效"。

顺带给 `run_task` 加了耗时日志：`task=safety affected=2 cost=37ms`，出问题能定位是哪个任务慢。

## 五、这轮之后还剩什么风险

1. **任务没有执行历史**：只有日志，没有库表。要查"昨天 3 点那次扫描做了什么"得翻日志文件。
   加 `task_run_log` 表可以解决，但要再动一次表结构，剩余时间不划算。
2. **保存点开销**：每条一个 savepoint，量大时有额外开销；当前批上限 500，可接受。
3. **HTTP 测试只覆盖读接口**：写接口（派单、闭环）在服务层已有覆盖，
   但"路由参数绑定 + 请求体校验"这一段没有端到端用例，属于已知缺口。
