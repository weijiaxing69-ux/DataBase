## 二、两个需要注意的地方

### 1. member2 的代码在仓库根目录

新增的是 `backend.py`、`billing_queries.py`、`seed_data.py`、`test_billing*.py` 这类独立脚本，
没有放进 `backend/app/modules/billing/`，也没有复用 `core/security.py` 的鉴权与 `shared/contracts.py` 的 Actor。

合并后会出现两套"后端"：骨架里的 `backend/` 和根目录的一堆脚本。
后续谁改计费、另一个要不要同步，很容易分叉。

**建议**：合并前让成员2 把业务代码搬进 `backend/app/modules/billing/`，
在 `app/main.py` 里 `include_router`，鉴权复用 `security.get_current_actor`。
根目录脚本可以作为工具保留，但要 `git mv` 到 `scripts/`。

### 2. member5 是完整子树

`member5/backend`、`member5/frontend`、`member5/database` 各有一套，
连 `core/auth.py`、`core/database.py` 都另写了一份。

好处是不影响主线，坏处是**演示时有两个前端、两个后端**，老师问"哪个是系统"会尴尬。

**建议**：二选一——
- A（推荐）：把 `member5/backend/app/modules/settlement/` 抽出来放进骨架对应位置，前端页面并入 `frontend/src/views/settlement/`；
- B：明确声明结算模块为独立演示子系统，报告里单独说明，不并进主应用。

## 三、建议的合并顺序

```
1) main 保持现状（骨架 + 资产 + 认证）
2) 合 member3-v1.0        ← 已验证 0 冲突，先合它最省事
3) member2 重构后再合      ← 搬到 modules/billing/，否则根目录会长期有人误改
4) member5 按 A 或 B 处理
5) 最后统一跑一次 database/bootstrap + 各模块 migrations
```

第 2 步之后建议立刻验证：

```bash
cd backend
python -m pytest tests -q                    # 应为 114 passed
python -c "from app.main import app; print(len(app.openapi()['paths']))"   # 应为 47
```

## 六、维护模块对外提供的东西（供其他模块对接）

| 能力 | 接口 | 说明 |
|---|---|---|
| 告警列表 | `GET /api/v1/maintenance/alerts` | 支持按桩、状态、等级、时间段过滤 |
| 派单 | `POST /api/v1/maintenance/alerts/{id}/work-orders` | 客服/管理员可代派 |
| 工单进度 | `GET /api/v1/maintenance/work-orders/{id}/events` | 时间线，可用于订单详情页展示"充电异常处理进度" |
| 运维统计 | `GET /api/v1/maintenance/stats/performance` | 按人/按站，可用于运营看板 |

计费与结算若需要"这次充电有没有伴随设备故障"，可以直接查 `device_alert` 的 `pile_id + occurred_at` 交集。
